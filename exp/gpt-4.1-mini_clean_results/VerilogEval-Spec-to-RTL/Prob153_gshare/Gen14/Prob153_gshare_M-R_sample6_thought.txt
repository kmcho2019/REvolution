Refactor the design by splitting prediction into explicit pipeline stages with separate registers and using combinational logic for prediction output signals aligned to the pipeline registers. Instead of registering `predict_taken` and `predict_history` outputs directly inside the sequential block, produce them combinationally from pipeline registers that capture the relevant state at prediction request time.

Key changes:

1. Capture prediction request signals (`predict_valid`, `predict_pc`) into registers on clock edge, along with GHR at that moment.  
2. Compute the PHT index from latched PC and history registers.  
3. Read PHT synchronously at the next clock to a prediction counter register.  
4. Produce prediction outputs (`predict_taken`, `predict_history`) combinationally from these pipeline registers, so outputs change immediately when pipeline stage registers update. This keeps outputs in sync and avoids glitches.

5. Separate GHR update logic into its own always block, using the priorities given: training misprediction recovery, then training update, else prediction update.

6. Use a synchronous RAM-style PHT update with training priority as before.

This refactor improves clarity by separating the pipeline stages and output logic, producing outputs combinationally from pipeline registers, and cleanly partitioning GHR update logic. This style should help align signals with testbench expectations and reduce mismatches.

Note: This keeps the 1-cycle prediction latency (prediction output available one cycle after predict_valid), consistent with synchronous RAM read behavior, but clarifies the output timing path.
