The main issue is that the `predict_history` output and the internal GHR update logic must use the exact GHR that was valid at prediction request time, to maintain timing correctness and output consistency.

To fix this, I will:

- Add a register to capture the GHR value at the moment of a valid prediction request, call it `predict_history_reg`.
- Use this latched GHR for both:
  - Outputting `predict_history` for the prediction request.
  - Computing the prediction index for the prediction request.
- Use the PHT value indexed by this latched GHR and PC to produce `predict_taken` combinationally.
- Store the predicted taken bit (`predict_taken_reg`) and valid flag from the *previous* cycle's prediction request.
- On clock edge, update the GHR:
  - If training valid and mispredicted, recover GHR to `train_history` (highest priority).
  - Else if previous cycle had a valid prediction, shift in `predict_taken_reg`.
  - Else hold GHR.
- Update PHT synchronously on training valid, using the training index (train_pc XOR train_history).
- Initialize PHT to weakly not taken (2'b01) on reset.
- Outputs `predict_taken` and `predict_history` are purely combinational and based on current valid prediction request and the captured GHR and PHT state.
- The update to GHR happens *after* prediction outputs have been generated, avoiding timing mismatch.

This design cleanly separates combinational prediction outputs and sequential updates, matching the spec and ensuring output correctness and timing order.
