To fix the functional correctness issues, explicitly separate and prioritize updates to the global history register (GHR) according to the spec:

- Maintain a single GHR register representing speculative global history.

- On each clock edge:

  1. If `train_valid` and `train_mispredicted` are asserted, recover GHR to `train_history` (committed history after flush). This has highest priority and overrides any other update.

  2. Else if `train_valid` (non-mispredicted), update the PHT entry indexed by `train_pc XOR train_history`. Do NOT update GHR here; GHR update only happens through prediction or misprediction recovery.

  3. Else if `predict_valid` (and no misprediction training), update GHR by shifting in predicted bit from PHT at index `predict_pc XOR ghr`. This represents speculative history extending with the current prediction.

- Reading the PHT is done combinationally from the current PHT state (before any synchronous update) so that prediction sees the PHT state before training update, fulfilling the spec's timing requirement.

- This ordering guarantees that when training misprediction and prediction occur in the same cycle, the training recovery takes precedence, discarding speculative updates from prediction.

- When `predict_valid` is low or training is inactive, GHR holds its previous value.

- The outputs `predict_taken` and `predict_history` are assigned combinationally based on current GHR and PHT.

- Initialize PHT to weakly not taken (2'b01) and GHR to zero on asynchronous reset.

This explicit priority resolves conflicts in GHR updates and ensures that history is consistent with the pipeline behavior described. It also matches the timing diagram specified in the problem.
