Implement the gshare branch predictor using a single global history register (GHR) representing the committed history and a separate speculative "shadow" history for predictions.

Key differences in this approach:

- Maintain one committed GHR (`ghr_commit`) which reflects the true history after training commits.

- Maintain a speculative GHR (`ghr_spec`) updated only on predictions.

- On prediction:
  - Compute index using `predict_pc ^ ghr_spec`.
  - Use a synchronous read of PHT using a small synchronous RAM model with registered output for timing clarity.
  - Output `predict_taken` and `predict_history` as the GHR before speculative update (i.e., current `ghr_spec`).
  - After prediction, update `ghr_spec` by shifting in the predicted bit, but do this in a separate pipeline register stage to ensure outputs correspond to the history before update.

- On training:
  - Update the PHT entry indexed by `train_pc ^ train_history` on the next clock edge.
  - If the branch was mispredicted, overwrite `ghr_spec` with the supplied `train_history` to rollback the speculative state.
  - Always update `ghr_commit` on every training to maintain committed true history.
  - When a misprediction training and prediction happen in the same cycle, give priority to the misprediction update to `ghr_spec` (i.e., recovery).

- For the PHT:
  - Use a synchronous RAM with registered read data.
  - On prediction, use the PHT output registered one cycle before to align timings, effectively having a one-cycle latency prediction output.

This pipeline latency means:

- Inputs `predict_valid` and `predict_pc` are registered and used to address PHT.

- The PHT output (2-bit saturating counter) is registered and used to produce prediction outputs for that cycle.

- The GHR update happens after outputting predictions.

This approach cleanly separates combinational and sequential logic, ensures output prediction history corresponds to the pre-update GHR, and handles misprediction recovery properly by prioritizing training state restoration of speculative history.

Because of one cycle latency in prediction outputs, users should expect `predict_taken` and `predict_history` outputs delayed by one cycle from `predict_valid` and `predict_pc`.

This tradeoff simplifies correct timing alignment and resolves the confusion of when to output the GHR state relative to updates, eliminating output mismatches.

The module will be fully synchronous and reset all state asynchronously on `areset`.
