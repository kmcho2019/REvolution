I will implement the gshare predictor with a slightly different architecture focusing on explicit pipeline registers and separated combinational vs sequential logic to clearly reflect the timing requirements and avoid subtle timing issues.

Key differences from the example solution:

- Use one global history register (ghr) updated only on clock edge.

- Prediction outputs are combinationally derived from ghr and PHT state read at current cycle, ensuring outputs reflect pre-update state.

- Prediction indexing uses predict_pc XOR ghr at cycle input.

- Training indexing uses train_pc XOR train_history (the history at the time branch executed), as specified.

- The 128-entry PHT is modeled as a reg array with synchronous writes only on train_valid.

- On clock edge, update PHT entry for training if train_valid, using saturating counter update.

- On clock edge, update ghr:

  - If train_valid & train_mispredicted: recover ghr to train_history.

  - Else if predict_valid: update ghr by shifting in prediction bit (taken/not taken).

  - Else hold current ghr.

- When training and prediction occur simultaneously, training misprediction recovery takes precedence for ghr update, per spec.

- The outputs predict_taken and predict_history are driven combinationally based on current PHT entry and ghr prior to clock edge update.

- The PHT read for prediction is purely combinational and reflects the pre-update state, so simultaneous train update does not affect current prediction output.

- The global history register update is carefully sequenced and implemented with explicit signals, avoiding potential race conditions.

This approach uses explicit combinational logic for outputs and synchronous logic for state updates to clearly match the timing diagram described, ensuring correct behavior and output consistency.

It also strictly follows the specified priority of updates and the behavior under simultaneous training and prediction.
