The key fix is to ensure that the `predict_history` output matches the global history register state *before* the prediction update, exactly as the spec requires. Currently, the prediction output (`predict_history_reg`) is latched from `fetch_ghr` at the clock edge when the prediction is valid, but `fetch_ghr` is updated later in the same clock edge, causing timing mismatches visible in simulation.

To fix this, separate the combinational read of the prediction global history from the registered output. Instead of latching `predict_history_reg` on the clock edge when `predict_valid` is asserted, directly assign `predict_history` combinationally from `fetch_ghr`. This way, `predict_history` always shows the state *before* the predicted branch update, since `fetch_ghr` updates only on clock edges.

For `predict_taken`, however, we still latch it to avoid combinational timing issues on outputs.

Additionally, simplify history registers to a single `ghr` register for clarity. Updates to `ghr` happen at each clock edge. On misprediction training, `ghr` recovers to the provided `train_history`. Otherwise, if a prediction is valid and no misprediction flush occurs, `ghr` shifts in the predicted taken bit.

Training updates the PHT synchronously on the clock edge. Predictions read the PHT combinationally and see the previous state before training.

Priority rules:

- On a cycle with both a misprediction training and a prediction, `ghr` recovers to `train_history` (flush recovery), ignoring the prediction update.

- Otherwise, if only prediction is valid, `ghr` updates with the predicted taken bit.

This matches the spec and ensures the outputs reflect the history used for prediction, avoiding stale or incorrect `predict_history` outputs.
