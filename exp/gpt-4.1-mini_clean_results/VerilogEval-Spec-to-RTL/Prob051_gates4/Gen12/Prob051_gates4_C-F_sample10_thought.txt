To fuse the best ideas from both examples, we combine the clarity, scalability, and direct synthesis-friendly style of Example 1 with the explicit procedural clarity of Example 2. 

Strategy:
- Use parameterized input width for future scalability and clarity.
- Declare outputs as `reg` to allow both continuous assignment or procedural assignment.
- Use an `always_comb` block (SystemVerilog) or `always @(*)` (Verilog) with a for-loop to explicitly calculate the reductions. This makes the logic style clear and synthesizable, aids code readability for maintainers who prefer procedural style, and explicitly shows the reduction process.
- Initialize accumulators explicitly to correct starting values.
- Avoid using synthesis attributes or overly complex constructs to keep the design portable and synthesis-friendly.
- Retain combinational logic nature (no registers or state).
- Use procedural assignments inside the `always` block to accumulate results for AND, OR, XOR.
- Keep the module parameterized with WIDTH, default 4.

This fusion gives:
- Clear, explicit logic for AND/OR/XOR reduction via for-loop.
- Scalability via parameter.
- Combinational behavior via always @(*) block.
- `reg` outputs for procedural assignments, consistent with the always block.
- Maintains a clean and maintainable RTL style, suitable for synthesis and easy debugging.

This style is a middle ground between fully continuous reduction operators and fully procedural loops, preserving synthesis quality and readability while showcasing explicit logic.

Note: Using SystemVerilog `always_comb` is ideal for clarity, but as the original question is in Verilog, use `always @(*)` for maximum compatibility.
