To improve correctness, the key is to robustly decode the sensor inputs to exact water levels for **all valid combinations**—not just four patterns—treating the sensors as thresholds: s[2] is highest, s[1] middle, s[0] lowest. The water level depends on which sensors are asserted starting from the top sensor:

- Above s[2]: all sensors asserted (s == 3'b111)
- Between s[2] and s[1]: s[2] is 0, but s[1] and s[0] are 1 (s == 3'b011)
- Between s[1] and s[0]: only s[0] asserted (s == 3'b001)
- Below s[0]: none asserted (s == 3'b000)

All other intermediate/invalid patterns should be handled deterministically, ideally as the closest logical water level (e.g., if a higher sensor is asserted without a lower one, treat carefully).

A simple, reliable method is to interpret `s` as a 3-bit thermometer code from highest sensor downward (s[2] high means above s2, else check s1, else s0, else below).

To detect sensor changes, store the previous sensor input, and on any change, update `prev_level` with old `curr_level`, then update `curr_level`. This avoids timing mismatches.

The supplemental valve (`dfr`) is asserted if the current level is higher than previous level (rising water), else 0.

On reset, set state to below s[0] (lowest level) with all flow valves and dfr asserted per spec.

This approach simplifies level decoding and state tracking, avoids undefined sensor states by mapping any unexpected pattern to the closest valid level, and sequences registers properly to prevent glitches or mismatches. It also improves robustness and correctness without unnecessary complexity.
