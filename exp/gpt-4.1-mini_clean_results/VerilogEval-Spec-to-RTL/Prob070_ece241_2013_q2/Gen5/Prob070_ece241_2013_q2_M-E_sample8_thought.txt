Since the inputs a,b,c,d represent a 4-bit binary number, and some input combinations never occur (3,8,11,12), we can treat those as "don't care" conditions during minimization.

Instead of directly writing the expressions for out_sop and out_pos from minterms and maxterms, we will:

1. Encode the inputs as a 4-bit vector `in_val = {a,b,c,d}` with `a` as MSB and `d` as LSB.
2. Create a 16-entry lookup table (LUT) that outputs 1 for 2,7,15, 0 for the specified zeros, and 'x' (don't care) for 3,8,11,12.
3. Use this LUT to derive minimal expressions for out_sop and out_pos via code, or directly implement the LUT in combinational logic.

For a clean design, we'll implement the LUT with a case statement inside a combinational always block to produce `out_sop`. The `out_pos` can then be generated by inverting the zeros and implementing minimal product-of-sums derived from the LUT (or by negating the `out_sop` and masking don't-cares).

Because the problem requests both minimized SOP and POS, we will:

- Implement `out_sop` as a case-statement based decoder from the LUT for clarity and correctness.
- For `out_pos`, use De Morgan's law on `out_sop` but also explicitly mask out the don't cares to avoid invalid inputs.

This approach ensures correct functionality regardless of simplification errors and leverages the "never occurs" states as don't cares by not specifying their outputs.

This differs from the prior approach by explicitly handling don't-care conditions via case statement and not assuming direct minimal expressions upfront.
